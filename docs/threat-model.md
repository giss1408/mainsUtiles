# petitGombo threat model

Kept current with each feature. Status values: `planned` (designed in the spec, not built),
`built` (code exists), `tested` (automated tests named in the last column).

The two harms that drive the design: a mini-jobber lured to a location (kidnapping, assault,
trafficking), and a household whose address and schedule are learned through a booking
(burglary, home invasion). Controls work by deterrence, exposure limits and fast response;
none of them makes harm impossible.

## Threats

Not built: applications, bookings, tracking and timers

| Forged guarantor bill | Both | Photo taken in the app only; the bill must be under 3 months old; staff call the guarantor and compare the holder's name | tested | `test_guarantor_submissions.py`, `test_guarantor_review.py` (age, name match, call required) |
| Guarantor's phone is the jobber's own number | Both | The number is normalised (`+225…`, `00225…`, spaces) and compared with the jobber's; refused as `guarantor_phone_own` | tested | `test_guarantor_submissions.py` (`test_guarantor_phone_same_as_jobber_is_refused_in_any_format`) |
| One bill backing many jobbers | Both | A bill reference may back at most `GUARANTOR_MAX_JOBBERS` jobbers, expired guarantors included; compared by keyed hash | tested | `test_guarantor_review.py` (`test_reference_cap_counts_expired_and_other_users_only`) |
| Insider reads guarantor data | Both | Name, phone and bill reference encrypted; the bill photo is served only through a permission-checked console view; every view and call is audited; the API never returns them | partly built | `test_guarantor_console.py`, `test_jobber_verification_api.py` (`test_response_never_contains_guarantor_name_phone_or_photo`). | WhatsApp spam to a third party's number | Third party | A jobber can only ask for a code; staff send it. | Trusted contact is the jobber or the guarantor | Both | The number is compared in any format with the jobber's own and the guarantor's; refused | tested | `test_trusted_contacts.py` (`test_own_phone_is_refused_in_any_format`, `test_guarantor_phone_is_refused_in_any_format`) |
| Swapping trusted contacts to evade the check | Both | A contact is never removed, only replaced; the replacement is confirmed by the same code; the old one counts until staff warned its number and the delay passed | tested | `test_trusted_contacts.py` (`test_replacing_a_confirmed_contact_keeps_it_until_...`, `test_no_service_removes_a_contact`) |
| Insider reads a trusted contact's data | Both | Name and number encrypted; staff see the name, and the number only inside the one-time WhatsApp link (console and staff app alike, `Cache-Control: no-store`); each view and send is audited; the jobber API never returns the number or the code | partly built | `test_trusted_contact_console.py`, `test_staff_contacts_api.py`, `contacts_screens_test.dart`, `test_jobber_contacts_briefing_api.py` (`test_no_response_contains_a_phone_a_code_or_the_answer_key`). Not built: reason-for-access prompts, alerts on unusual volume |
| Briefing answered by guessing or copied | Mini-jobber | A wrong answer shows why but nothing is learned about the key from the cards API; the briefing is a safety lesson, not a gate against a determined jobber | built | `test_briefing.py` (`test_cards_never_expose_the_answer`) |
| Account lending or substitution | Household | Door handshake with selfie match (6); one account per identity document | planned | |
| Address harvesting | Household | Blurred listings, address released only to the booked jobber and expiring at check-out (3); weekly release limits; address access log (9) | partly built | Offers expose the commune and quartier only, never the address, position, name or phone number (`test_offers_api.py`, `test_my_offers_api.py`). Not built: address release at booking, weekly limits, access log |
| Collusion between accounts | Both | Linked accounts do not build trust; ratings only between unrelated accounts | planned | |
| Forged or reused documents | Both | In-app camera capture only; reuse detection on images and customer numbers; staff review | partly built | Built: photos taken only with the in-app camera; the same image on two accounts is flagged; one identity document number and one bill or certificate number per account, compared without case or punctuation; under-18 and expired documents refused (`test_verification_submissions.py`, `test_verification_review.py`). Not built: liveness, automatic document checks; a person compares the selfie with the document |

| Relayed QR codes | Both | Signed, short-lived, device-bound, rotating codes; screenshot blocking | planned | |

| Fake support agents and cloned apps | Both | "Staff never ask for this number" wording in every confirmation; official-channels page | built | `test_enrolment_screens_test.dart` (code screen note); official-channels page not built yet |
| Payment fraud | Both | Idempotent payment states; signed webhooks; cash confirmed by QR scan | planned | |
| Harassment | Both | In-app chat with contact filtering (7); block and report; human review (8) | planned | |
| Data breach | Both | Field-level encryption for addresses and identity data (9); no secrets or codes in logs; hashes only for codes and tokens | partly built | Built: identity photos, names, dates of birth, document numbers and home positions are encrypted with `FIELD_ENCRYPTION_KEY`; photos are served only through a permission-checked console view that logs every view; the householder API never returns them (`test_encryption.py`, `test_verification_api.py`, `test_verification_console.py`). Not built: key rotation, reason-for-access prompts, second-staff approval, alerts on unusual read volume |
| Insider misuse | Both | Role permissions; append-only audit of staff actions; no bulk export; second approval for sensitive actions (9) | planned | |
| Stolen staff password | Both | Staff sign in with a password and a phone activated by an administrator; one active phone per staff member; lock after 5 wrong passwords; 10-minute access tokens; staff phones revocable from the console | tested | `test_staff_api.py` (all) |
| Leak of numbers from a staff phone | Both | Staff app blocks screenshots and screen recording; the WhatsApp link with the confirmation number is opened and dropped, never shown, stored or logged; tokens in memory only | built | `screens_test.dart` (WhatsApp send), `staff_controller_test.dart` (nothing written to storage); screenshot blocking not checked on a phone |
| Dodging enrolment limits with a forged network address | Both | Client address taken from the reverse proxy's own `X-Forwarded-For` entry, only when `TRUST_PROXY_HEADERS=1`; application port not published | tested | `test_production_settings.py` |
| Sock-puppet or mass applications to win offers | Householder | Only a J1 jobber applies (checked again at accept); one live application per offer, at most `APPLICATIONS_MAX_OPEN` waiting per jobber and `APPLICATIONS_MAX_PER_OFFER` per offer | tested | `test_applications.py` (`test_only_a_j1_jobber_can_apply`, `test_open_applications_cap_and_offer_cap`) |
| Application message used to move the talk off the platform | Both | Email, phone numbers and off-platform terms are refused, not queued | tested | `test_applications.py` (`test_message_with_contact_details_is_refused`) |
| Double accept, or two offers at the same hour, creating two bookings | Both | Offer and application rows locked; one live booking per offer (database constraint); an overlapping booking refuses the application | tested | `test_accept.py` (`test_two_devices_accepting_at_once_make_one_booking`), `test_booking_models.py`, `test_applications.py` (`test_overlapping_booking_is_refused_and_a_neighbouring_one_is_not`) |
| Identity leak through the applicant card or the offer detail | Both | The householder sees a first name, tier and counts; the jobber sees a trust line; no phone, id, last name or address either way | tested | `test_applicants_api.py`, `test_applications_api.py` (`test_no_jobber_response_contains_the_householder_name_phone_or_id`) |
| An applicant who lost verification being accepted | Householder | J1 is checked again inside the accept transaction | tested | `test_accept.py` (`test_accept_refused_when_the_applicant_lost_j1`) |
| Fake or reused payment screenshot | Householder, platform | Staff confirm against the platform account's real history with two explicit checks; the console warns when the same image was sent for another payment; every proof view is audited | tested | `test_payment_review.py` (`test_both_checks_are_required`, `test_proof_seen_before_flags_the_same_image_on_two_bookings`), `test_payments_console.py` |
| One transaction reference paying for two bookings | Platform | A reference (any case, spaces or dashes) confirms only one booking: service check and database constraint | tested | `test_payment_review.py` (`test_the_same_reference_cannot_confirm_a_second_booking`), `test_payment_models.py` |
| Staff or an insider approving an unpaid booking | Platform | Only the `payment_agent` group can confirm; every decision and every proof view is audited with the actor; a double decision is refused | tested | `test_payment_review.py` (`test_without_the_permission_nothing_works`), `test_accept.py` (threaded double decision) |
| Receiving numbers changed to an attacker's account | Householder | Only the `payment_agent` group edits methods; each change is audited with the number | tested | `test_payment_methods.py` (`test_agent_manages_methods_and_the_number_is_normalised_and_audited`) |
| Exact address learned before the booking is paid, or after the job | Householder | The pin is returned only to the booked jobber, for a paid booking, inside the release window, never after cancel or the job; every read is audited and the response is not cached | tested | `test_address_release.py`, `test_payments_api.py` (`test_address_endpoint_obeys_the_window`) |
| Jobber's name or photo learned before payment | Jobber | Released to the householder only for a paid booking; the photo endpoint is not cached; both views are audited | tested | `test_address_release.py` (`test_jobber_card_needs_a_confirmed_booking_and_is_for_the_householder_only`) |
| A refund never made, or made twice | Householder | A cancelled paid booking becomes a visible refund-due line, recorded once with a reference and an actor | tested | `test_booking_cancel.py` (`test_record_refund_needs_the_permission_a_reference_and_happens_once`) |
| Payment service used with no way to pay | Both | With no active method with a number, apply and accept are refused | tested | `test_payment_methods.py` (`test_no_active_method_means_apply_and_accept_are_refused`) |
| Insider reads a payment reference or receipt, or decides without the right | Householder | The list shows no reference; the detail and the image only for payments in the queue the member may work (`verify_payment` or `make_refund`), audited, never cached, dropped from the phone when the screen closes | tested | `test_staff_payments_api.py`, `payments_controller_test.dart` (`test_neither_the_state_nor_the_storage_holds_the_reference_after_close`) |
| A payout made twice, or on a refunded booking | Platform | One payout per booking (`OneToOne`, `get_or_create`); recorded once under a row lock; refused when the payment was refunded in full; a split pays only the jobber's share | tested | `test_payouts.py` (`test_double_payout_is_invalid_state`, `test_a_refunded_booking_is_never_paid`), `test_reports.py` (`test_split_pays_part_and_refunds_the_rest`), `test_job_completion.py` (`test_confirming_twice_makes_one_payout`) |
| A jobber paid without doing the job | Householder | Check-in distance to the home pin recorded and flagged; the householder confirms or has 24 h to dispute; a dispute freezes the payout; no check-out ends in a dispute; no check-in ends in a refund | tested | `test_check_in_out.py` (`test_a_far_check_in_is_flagged_for_staff`), `test_job_completion.py`, `test_reports.py` (`test_a_dispute_freezes_the_booking_and_the_payout`). The distance is not enforced, and fake GPS is not detected |
| A householder who never confirms, to avoid paying | Jobber | The job completes by itself after `RELEASE_TIMEOUT_HOURS` and the payout is created | tested | `test_job_completion.py` (`test_timeout_completes_by_itself_and_audits_the_system`) |
| A false dispute to avoid paying | Jobber | One open dispute per booking, only before completion; staff decide with a required reason; the payout is frozen only until then | tested | `test_reports.py` (`test_a_second_dispute_becomes_a_concern`, `test_a_dispute_after_completion_is_refused_but_a_concern_is_kept`, `test_resolving_needs_the_permission_a_note_and_an_open_dispute`) |
| Review blackmail, retaliation or a contact leak | Both | A review is hidden until both are in or seven days pass; comments with a number or an off-platform contact are refused; only completed bookings, once per side | tested | `test_reviews.py`, `test_jobs_api.py` (`test_review_flow_through_the_api_hides_the_other_side_until_both_are_in`) |
| Insider reads a jobber's phone on the payout page, or a report's text | Jobber | Phone shown only to holders of `make_payout`, each view audited, page never cached; lists show no phone, text or reference; opening a report is audited | tested | `test_jobs_console.py` (`test_payout_page_shows_the_phone_audits_and_is_no_store`, `test_lists_show_no_phone_text_or_reference`, `test_without_the_permission_gets_403`) |
